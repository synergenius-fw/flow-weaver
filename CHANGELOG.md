# Changelog

All notable changes to this project are documented in [GitHub Releases](https://github.com/synergenius-fw/flow-weaver/releases).

This project follows [Semantic Versioning](https://semver.org/) during beta. Breaking changes may occur between minor versions until v1.0.

## 0.42.2

- **The spine keeps a scope owner above its body.** When a loop wired its scoped children's failure arms into its own `failure` input, the diagram's shared-failure-join pass treated the owner as a join and drew it below its own body, inverting the loop. A node entered only by its own scoped children is the loop reporting failure, not a join, so it now keeps its place at the head of its body.

## 0.42.1

- **A durable loop can wire its failure path out.** The convergence check refused a scoped gate whenever any branching node sorted before it, and a scope owner always sorts before its scoped children — so wiring the loop's own `onFailure` (surfacing a failed iteration instead of losing it) falsely tripped "durable boundaries after branch convergence". The check now counts a branching node against a boundary only when the boundary is actually in that branch's reach, so an in-scope gate is no longer flagged for its own loop's downstream arms. A genuine post-convergence gate (fed by both arms of a real branch) is still refused. `examples/research-agent-loop.ts` now wires its failure path and validates clean.

## 0.42.0

This entry consolidates the 0.39.0 to 0.41.1 releases, which have no entries of their own.

- **Loops inside durable workflows.** A scoped node (a `forEach`/iteration or agent loop) may now sit inside a workflow that pauses at a durable gate, as long as the loop is bounded (a `max`/`limit`/`attempts`/`iterations` input on the scope node) and sequential (its body awaits one iteration at a time, no `Promise.all`). Each iteration can pause at a gate or effect and resume at the same iteration in a fresh process: the iteration ordinal is reconstructed from committed continuation state rather than an in-memory counter. A concurrent or unbounded scope that reaches a gate is still refused, now naming the scope and what it needs instead of banning all scopes. This is what lets a ReAct / tool-use agent loop be durable. `examples/research-agent-loop.ts` shows the shape.
- **Console: words for the person answering, and a way in for the first-timer.** The gate card now shows the gate function's description as what is being asked, names each handed-over input by its `@input` label, and puts each `@output` label under the field that answers it, so an approver reads the author's words rather than a type. The Project page names the workflows with errors in its first line, and in a project where nothing has run yet leads with a **Start here** card that runs a workflow with one click. The header chip reads *not compiled in place* and says why that is not a problem. Where the console said an agent gate without a profile "waits for a person", it now says whoever drives the run answers it, here or over MCP, since an assistant is often that driver. The clock lines say "checked every few seconds" rather than "tick".
- **The coordinator owns time.** A new built-in, `sleep`, is a `timer` gate: the run pauses with a wake time and the process is free to go, unlike `delay`, which holds the process and is now documented as being for short pauses only. A gate given a `timeout` input (`waitForEvent`'s, or an input of that name on a gate of yours) gets a deadline, where before the value was recorded and never acted on. Both live in one field on the run, `due: { at, action: 'wake' | 'timeout' }`, shown by the console (with **Wake now** on a sleeping run), the API and `fw_runs`. `runs.tick()` on the coordinator is the clock: it wakes what is due and sends a timed-out gate along its failure path with the reason `no answer within <timeout>`. `fw serve` ticks with its sweep, the console every few seconds, `fw_runs` before it lists, and several tickers on one store never move a run twice. `fast: true` answers a `sleep` at once. The fourth gate kind, `timer`, appears in `@durableGate`, the continuation format and every place that names the kinds.
- **The compiled file carries the durable engine.** A compiled workflow file now runs with nothing from the package: its runtime section includes the engine behind gates and effects (the package's own `continuation-core.ts` and `durable-execution.ts`, copied in as text, so there is one engine), and the file exports `createWorkflowRuntime`, `acceptContinuation`, `isDurableGateYield`, `DurableGateYield`, `CancellationError`, `createContinuationEnvelope` and `ENGINE_VERSION` beside its workflows. A gate-free workflow is called with the runtime the file builds. A gated one throws `DurableGateYield` with a complete `continuation`, and a host with any JSON store brings it back through `acceptContinuation` and resumes, as the *A host of your own* section of the `library` topic shows. Every gated body now declares its graph fingerprint to the engine first (`ctx.bindWorkflow`), so a continuation from a changed graph is refused before a node runs, by the coordinator and a host alike. `createWorkflowRuntime` takes an optional `bundleDigest` for hosts that hash their own builds. The executor, the artifact compiler and the generator compute that fingerprint with one function (`graphIdentity`), without source locations, so a temp copy of a file has the same identity as the file. `fw init`'s runner imports the runtime helper from the workflow file. The README's licence summary no longer counts the runtime helper as use of the package, since it is output. Package users: `WorkflowRuntime.durable` is now the `DurableEngine` interface rather than the class. `acceptContinuation` and `DurableEngine` are exported from the root and `./runtime`.
- **An `approval` template, and `fw agents`.** `fw create workflow approval <file>` (and `fw_scaffold` with `template: "approval"`) writes a gated workflow: prepare a request, pause for a person at a `@durableGate approval`, carry it out on approval or take the failure path on refusal. It validates clean and runs through the coordinator as generated. `fw agents` lists the project's agent profiles with their readiness and gate mapping, never a key. `fw agents --init` writes the starter `.flowweaver/agents.yaml`, and `fw serve` says so when the file is missing. The `fw_scaffold` tool and the scaffold topic now say that they, `fw create` and `fw templates` are one thing. Init's persona texts no longer quote tool and template counts that had drifted.
- **First run, fixed.** `fw init` no longer installs the "Weaver AI assistant": the pack it named is not on the registry, so `npm install` failed for every project made with the defaults, and the getting-started notes pointed at `fw weaver …` commands that do not exist. The `--with-weaver`/`--no-weaver` flags, the `.weaver.json` file and the `GETTING_STARTED.md` are gone. The generated `src/main.ts` now builds a runtime with `createWorkflowRuntime` and hands it to the workflow, so `npm start` runs instead of failing with `Cannot read properties of undefined (reading 'services')`, and its "not compiled yet" check matches the stub's actual message. Next steps name `fw console --open`. `fw run` on a gated workflow now says what to use instead of the engine's "coordinator-verified whole-bundle identity". A run started without a required parameter used to run and return nothing for it, which read as success. Now `fw run`, `fw_run`, the console and the API refuse it, naming the parameter (`MissingParamsError`, `MISSING_PARAMS` over MCP, `400` over HTTP). `fw run --debug` stepped with an empty execution order because it handed the parser the file's text instead of its path, now fixed. The *See:* links under validation errors pointed at `docs.flowweaver.dev`, which no longer exists. They now point at the reference pages in the repository. `fw --help` describes the tool.
- **Less noise for assistants.** `fw_runs` lists the newest 20 runs by default, with `limit` and `status` (ask for `waiting`) to narrow, instead of every run ever made on the machine. `fw_docs search` and `fw docs search` drop filler words, require a section to cover at least half of a multi-word query, weight a heading that names the thing over a body that mentions it, and count the topic's own name; "expose workflow as HTTP endpoint" now finds *Deployment › Workflows as endpoints* first rather than a section on async workflows.
- **The console runs the project's services.** A Project page (the dashboard glyph on the left bar, and where the console opens with nowhere else to go) puts the controls on the concerns. A Server card starts, stops and restarts `fw serve` with saved settings (port, host, a token generated per start and shown, agents, trace, Swagger, dev, start-with-the-console), shows its URL, token and request count, and lists a server started from a terminal with a Stop of its own. `fw watch` appears as a *recompile on save* switch, Endpoints and Agents with the number that matters, the editors' MCP registrations, and `fw doctor`'s checks, and on the right sit every run waiting at a gate and the latest failures. Services the console started stop with it. Settings live per project under `~/.fw/console`. A bottom drawer, reachable from every page, streams the Server and Watch output and hosts the CLI, which leaves the right column. Reference, Changes and Export fold under **More**. Overview, Endpoints and Agents share one header. The Serve pane and the Endpoints page start and stop the server too, and *copy request* fills in the running server's token. Status is now part of the Project page. `createConsoleServer({ services })` lets a test hand in a fake spawn.
- **`fw serve` runs gated workflows.** The server now goes through the local coordinator, the same run store as `fw console` and `fw_run`. `POST /workflows/<name>` answers `200` with the result, or `202` with a `runId` and the labelled gate when the workflow pauses. `POST /runs/:id/resolve`, `GET /runs/:id`, `GET /runs`, `POST /runs/:id/cancel` and an SSE stream at `GET /runs/:id/events` follow the run through. `?async=1` answers before a segment ends. A bearer token (`--token`, `FW_SERVE_TOKEN`) guards every route but `/health`. The default host is now `127.0.0.1`, and listening beyond loopback needs a token or `--insecure`. `--trace` keeps and streams a step trace, `--dev` puts stacks in errors and accepts mocks, `--cors` is off unless asked for. The response shape changed from `{ success, result }` to the run, and `fastify` is no longer needed. `/openapi.json` describes all of it, including the run resources and the bearer scheme.
- **Agent profiles answer agent gates.** `.flowweaver/agents.yaml` maps a gate (by `workflow/node`, by its `agentId`, or a default) to a profile: `anthropic`, `openai`-compatible (Ollama, Groq, vLLM…) or `claude-cli`, a model, the environment variable its key is read from, a system prompt and a turn limit. A run that pauses at a `waitForAgent` gate is answered by the matching profile from inside the process: the model gets the gate's inputs and a `submit_answer` tool shaped from the gate's output type (and `reject` when there is a failure port), calls it, and the run resumes. A profile that is not ready, a model that never submits, or an answer that does not fit leaves the run waiting with the reason recorded, for a person. The run record carries `agent: { profile, status, usage }`, and the transcript is kept beside the run. `@synergenius/flow-weaver/agent` exports the profile loader and `answerGate`, and `@synergenius/flow-weaver/coordinator` exports `answerAgentGate` and `autoAnswerAgentGates`. Keys are never stored. The console shows only whether the variable is set.
- **Workflows as endpoints: `@http`.** A workflow declares its route (`@http POST /reviews`, `@http GET /reviews/:path`, with `mode=async`, `auth=none` and `callback` flags) and `fw serve` mounts exactly that. Path segments bind parameters by name and type, `GET`/`DELETE` read the rest from the query, and the other methods read from the body. A bad parameter is `400` with the field named. The answer is the workflow's return ports: `200` on `onSuccess`, `422` on `onFailure`, `202` with `Location` when a gate pauses the run, `500` on failure. An `Idempotency-Key` makes a retry the same run. A `callback` route POSTs the final response to the caller's `callbackUrl`, HMAC-signed with the server token. Routes under the API's own paths, or declared twice, are refused and reported. The tag round-trips through `fw compile` and `fw_modify`, and `HTTP_PARAM_UNKNOWN` catches a `:param` that is not a parameter. `/openapi.json` describes the declared routes.
- **The API is embeddable.** `@synergenius/flow-weaver/server` exports `createWorkflowApi({ dir, token, agents, trace, runsDir, legacyRoutes })` with `node()`, `express()` and `fetch()` adapters and a transport-agnostic `handle(req, res, { basePath, body })`, so the same routes run under `http.createServer`, `app.use('/api', …)` in Express, a Fastify route, or a fetch host such as Bun, Hono or a Next.js route handler. Links and `Location` are written under the mount path. A body a framework already parsed (`express.json()`) is used as is, and form posts are accepted. `onRun` and `onCallback` hooks feed logs and metrics. `fw serve` is now a thin wrapper around it. Every run records its `origin` (`http`, `console`, `mcp`).
- **Runs live in a store you can replace.** The coordinator keeps everything through a `RunStore`: nine methods over a run's record, named JSON documents beside it (continuation, trace, effect receipts, transcripts, callback state) and a claim while a process drives it. `createFileRunStore` is the default and keeps the `~/.fw/runs` layout as it was. `createMemoryRunStore` serves tests. `createLocalCoordinator({ store })` and `createWorkflowApi({ store })` take yours, and `checkRunStore` from `@synergenius/flow-weaver/testing` runs the contract against it. While a segment runs the run is claimed, so two processes on one store never drive the same run at once, and the loser gets `RunBusyError` (`409 RUN_IN_FLIGHT` over HTTP, `RUN_BUSY` over MCP). **Breaking for library callers:** every coordinator method now returns a promise (`await runs.record(id)`, `await runs.list()`, `await runs.cancel(id)`), because a store may be remote.
- **The API holds up under real traffic.** A request waits at most `maxWaitMs` (60 s, or `Prefer: wait=<s>` for less) before answering `202` with the run to follow, so a proxy timeout never loses a client its run id. `maxInFlight` (32) caps concurrent segments with `503` and `Retry-After` past it. `GET /runs/:id/result` answers in a declared route's own shape (`202` while waiting or running, `200`/`422`, `500`, `410` when cancelled) and is what `Location` points at, so a client reads one shape end to end. An agent answer in progress records its process, and a crash mid-answer no longer locks the gate: the next server or console to start reclaims it, and a resolve ignores a note whose process is gone. `--swagger` now works behind a token: `/docs` and `/openapi.json` are readable without it when docs are on, and `/docs` is `404` otherwise.
- **Callbacks are delivered whoever finishes the run, and only to public hosts.** A `callbackUrl` is kept beside the run, and the API sweeps for finished runs still owing one, so a gate answered in the console or by an agent still fires the callback, a restart does not lose it, and a failed delivery is retried with growing delays before it is recorded as given up. Private, loopback and link-local addresses, and names resolving to them, are refused with `400 CALLBACK_REFUSED` unless the embedding names its hosts or `fw serve --dev` allows them, and redirects are not followed. An `Idempotency-Key` reused with different parameters is `409 IDEMPOTENCY_MISMATCH` rather than a silent replay. `fw openapi` now writes the same document `fw serve` publishes, declared routes included, with `--no-auth` and `--no-legacy`.
- **Console: Endpoints, and an agents editor.** An Endpoints page (the API glyph on the left bar) lists every declared route in the project with what it answers and the `curl` to copy, the routes that could not be mounted, and whether `fw serve` is up. Its side has the mounting snippets. The Serve pane lists the open workflow's routes and, for one without any, a single **Expose as endpoint** button that writes the `@http` line. **Edit** is a small route editor (method, path, three switches) that rewrites only those lines. The Agents page is now an editor: pick a provider from three cards, fill a short form (model suggestions per provider, the key variable checked live, never the key), **Try it** sends one turn and reports the reply time, and the gate mapping is a select per gate. The New run card picks the profile per agent gate. Run rows say when a run came over HTTP or MCP.
- **Console: Agents and Serve.** An Agents page (the robot glyph on the left bar) reads the project's profiles, their readiness and the gate mapping, and offers the starter file. The New run card gains an Agents section naming the profile each agent gate would go to, with a per-workflow switch to have them wait for a person instead. While a profile answers, its panel sits on the step's row with the streamed words, tool calls and tokens. Afterwards one line remains. On failure the form is back with *ask the agent again*. A Serve pane on the workflow says whether `fw serve` is up for the project and gives the `curl` for the open workflow with the run form's parameters, plus the run URLs. The `ClaudeCliProvider` gains `allowedTools`, used by the gate resolver to switch every built-in tool off.

## 0.38.0

- **`fw console`: a local operator console.** One command opens the project in the browser: workflows as processes on a lane spine (bodies in a named band, failure arms, pulled steps), live runs with per-step timing and per-pass values for steps that run once per item, gates answered from a form built from the port's TypeScript type, a step-through debugger with breakpoints, an Issues pane, a Reference pane, a CLI pane with completion, packs and marketplace views, a Status page, and ⌘K search. The **New run** card builds parameters from the types, keeps presets, and can answer gates and calls with **mocks** so a gated workflow runs unattended. **Changes** compares two git versions of a workflow as one marked picture with Before/After on the same rows, and every run is stamped with its commit. See the `console` topic.
- **Artifacts for stakeholders.** `fw artifact --kind brief|pdf|svg` and the console's Share menu produce an interactive one-screen brief, a printed PDF (one-page overview then every step) via the Chromium on the machine, and the spine as an SVG. The old SVG/HTML diagram renderers and the process page are gone. `fw diagram` draws the spine.
- **Mocks answer gates.** `FwMockConfig` gains `gates` (an answer for any gate by node id); `events`/`agents` answer their gates at the boundary instead of pausing, and `node:*` answers a node whatever key it asks with. Mocks travel with the run for later segments.
- **Grammar:** `[position: x y]` / `@position` are removed. Legacy files parse with a warning and `fw compile`/`fw migrate` rewrite them clean. Any Material Symbols name is a valid `@icon`, in snake_case or camelCase.
- **Library:** `@synergenius/flow-weaver/coordinator` is a package export. A new `library` topic covers calling compiled workflows, and pack authoring and the *Extending the grammar with a pack* section are documented, with `HND-001`/`HND-002` pack checks.
- **Removed:** the platform commands (`login`, `logout`, `auth`, `apikey`, `ai`, `account`, `org`, `deploy`, `undeploy`, `cloud-status`, `connect`) and everything behind them.
- Also: `fw_diagram` formats are `svg`, `ascii`, `ascii-compact`, `text`. Run history rows say what happened, and durations read as `1m 25s`, not `84880.0 s`.
- **Docs:** the durable-gates topic gains a "Validate the answer" section. Resume verifies the run, bundle, graph and engine version but not the answer's content, so the deterministic part of the workflow should check an agent gate's reply before acting on it. The worked example puts a normal-mode `@durablePure` node after the gate that returns the checked value on `onSuccess` and routes a malformed reply to `onFailure`. It is a runnable use-case (`use-cases/agent-gate-demo/review-with-validation.ts`) with a test pinning both routes.

- **Docs:** the node-conversion and orientation topics teach the minimal `@expression` form. For a typed function, `@flowWeaver nodeType @expression` is the whole annotation, and ports are inferred from the signature. `@input`/`@output`/`@label` are documented as optional overrides (a description, a rename, an order, a label), not a transcription step. `INFERRED_NODE_TYPE` is clarified: it fires only when a function has no `@flowWeaver nodeType` at all, not when port tags are omitted. The expression-reference section now says to keep expressions short and put a prompt or any multi-line string in a node function body, not in a `[expr:]` string.
- **Fix:** an `[expr:]` reference to an upstream port whose name equalled the target port name compiled to a bare node id (`const ap_factor = cfg.factor`) and crashed at run time with `cfg is not defined`. The reference is now fetched from the context and substituted whatever the connection's origin, so `[expr: factor="cfg.factor"]` works like the cross-named case. Found by dogfooding, with regression tests covering the same-name, cross-named and mixed-expression shapes.
- **An `@expression` node in a gated workflow needs no `@durablePure` tag.** Expression mode is a pure input-to-output function by construction, so it is classified pure automatically, matching how the code generator already treats any non-gate, non-effect node. Normal-mode pure nodes still write `@durablePure`, and gates and effects still need their tag. The classification rule, previously duplicated in the closure validator and the compile check (which is how it briefly disagreed with itself here), now lives in one shared `durableClassificationCount` helper.
- `DESIGN_ASYNC_NO_ERROR_PATH` now says what a failure does for each node mode. For a normal-mode node the advice is unchanged: wire `onFailure`. For an `@expression` node the warning, the friendly text, the MCP hint and the error-codes entry now state that a throw aborts the run with the error and that wiring `onFailure` changes nothing. To route the failure, write the node in normal mode and return `onFailure`, or suppress the warning if aborting is intended. When the rule fires is unchanged. A test pins the runtime behaviour the wording describes, so the two cannot drift apart silently.
- **Expressions can reference upstream ports.** Inside `[expr: port="..."]`, `Start.<param>` and `<node>.<port>` (with any further property access) read values the workflow already has. Each reference becomes a connection marked as derived from the expression, so ordering, cycle detection, `fw_query`, the diagram and the durable continuation all see the dependency. The generator fetches the values and substitutes them before evaluating. A derived connection is never written as `@connect`, is exempt from the one-source and type-compatibility rules, and cannot be removed on its own. Unknown ports, control ports, self-references, scope-crossing references and names that are also top-level bindings of the file are parse errors that name the instance and port. No existing file changes meaning: a reference could not work before, and an expression without one produces no derived connection. See ADR 0002.
- **`@path` resolves Exit ports by name.** A `@returns` port now resolves to the nearest earlier step with a same-name output, like any other step's input, so a linear pipeline with consistent port names needs no `@connect` at all. An explicit `@connect` to the port wins, and a `Start` param never resolves straight to Exit. The only observable change for an existing file is an Exit port that was unconnected and reported by `UNREACHABLE_EXIT_PORT`, which now receives its value. Connection order is unchanged, so graph fingerprints of unchanged files are unchanged.
- Docs teach the compact form: the orientation model leads with `@expression` and `@path`. The tutorial, concepts, durable-gates, built-in-nodes, iterative-development and export-interface examples are rewritten in it and validated. The `sequential` and `foreach` templates generate it, with a test that validates and runs both. The docs now state what a throw in an expression node actually does: it marks the node failed and propagates out of the workflow call, so routing a failure to another node still needs a normal-mode node.
- The durable-gates topic now says that an **effect** after branch convergence is refused, not only a gate. A test pins the engine's behaviour.
- **Breaking (MCP):** removed `fw_create_model`, `fw_implement_node` and `fw_workflow_status`. They generated an undocumented stub form that the rest of the pipeline could not process (no `(execute, params)` workflow signature, single outputs renamed to `result`, no durable classification) and made the authoring path more confusing than writing the file. The `flow-weaver-nocode` prompt, the `fw init` persona prompts and the orientation topic now say to write the workflow file directly.
- `fw_modify`, `fw_modify_batch` and `fw modify` rewrite only the JSDoc annotations. A file that has not been compiled in place stays uncompiled instead of growing a runtime section and generated body on its first structural edit. A file that was already compiled in place is still recompiled so its body stays consistent.
- In-place generation now round-trips `@durablePure`, `@durableGate <kind>` and `@durableEffect`, both on authored node types and on the built-in gates it inlines. Previously a compiled gated workflow lost every classification on re-parse and `fw_run` failed with "waitForAgent requires a generated durable agent gate".
- `addConnection` is idempotent: a connection that already exists (explicitly or through `@autoConnect`) is skipped with a warning instead of failing the whole batch.
- MCP validation items carry one next step, `hint` or `fix`, instead of a `friendly` block whose title and explanation restated the message.
- `OBJECT_TYPE_MISMATCH` is no longer reported when either side is an opaque object type (`object`, `Record<string, unknown>`, `{}`) or the target is `unknown`, so the built-in gates' `context` and `agentResult` ports connect without a false warning.
- Docs: the orientation loop no longer points at a generator. `jsdoc-grammar` documents the `@flowWeaver node` shorthand, and `mcp-tools` and `durable-gates` describe the annotation-only edit behaviour.
